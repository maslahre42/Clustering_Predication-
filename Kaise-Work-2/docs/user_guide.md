# SmartWasteRouting — user guide (M13, refreshed for v4 semantics + scenario engine, M16)

Explainable glass-waste collection forecasting and route-optimisation
prototype for the PreZero / City of Heilbronn challenge. This guide covers
what the app does, exact commands, a screen walkthrough, and the technical
architecture (challenge deliverable 4).

Status labels used throughout: **[observed]** = verified in the challenge CSV
(`docs/data_profile.md` is the data dictionary — do not duplicate it here) ·
**[predicted]** = model/solver output · **[representative]** = value supplied
verbally by the challenge representative (14 Nov 2026), configurable ·
**[representative-stated]** = project-owner statement of data semantics
(14 Nov 2026; written confirmation pending) · **[literature]** = sourced
external reference (citation beside the value) · **[demo assumption]** =
labelled synthetic value, configurable, not from data. Inputs still awaited
from the host are tracked with their current labelled defaults in
`docs/open_questions.md` (Q1–Q11). Comparison demo numbers below come from
`docs/demo_numbers.md`, regenerated by `.venv/bin/python -m src.api.compare_demo`
(2026-11-14, v4: fixed-frequency status quo + density 0.40 [literature]); the
scenario-engine numbers come from live `POST /api/scenarios` /
`POST /api/simulation` runs recorded in the same file.

## 1. What the app does (plain language)

The city has 449 glass-collection locations with 1,338 container series
(location × colour: brown/green/white) recorded over 11,701 **emptying
records** (DE "Leerungsdaten") from 2025-10-17 to 2026-09-30 [observed].
One row = one emptying event; the fill level is what the container showed
when the schedule reached it [representative-stated — written confirmation
pending]. The app answers five questions:

1. **Which containers will need emptying soon?** A persistence forecast
   (last known fill level) predicts the next emptying record per series.
2. **Which ones should we collect?** A threshold policy (default 80 % +
   always-include overfull) selects candidates and explains every skip.
3. **In what order should trucks visit them?** OR-Tools plans routes and
   recommends the fleet size; every numeric default is a visible label —
   [representative] (supplied verbally by the host), [literature] (density)
   or [demo assumption] — until real data replaces it.
4. **How long until each container is full?** A per-series fill-at-emptying
   rate converts into days-to-full [predicted] — the reporting the challenge
   representative asked for.
5. **What if the schedule changed?** The scenario engine (§3, Scenarios tab)
   replays fixed-frequency vs demand-driven emptying and reports **cost and
   service level together** — never cost alone.

There is one active dataset in memory; uploading replaces it.

## 2. Setup, run, test, demo (exact commands)

Prerequisites: Python 3.14 (3.12–3.14 supported; see `README.md` for
versions), uv ≥ 0.13.1, Node ≥ 26. Clean checkout needs **no API keys**
(`.env.example` is optional app settings only).

```bash
# backend
uv venv --python 3.14
uv pip install -e ".[dev]"
.venv/bin/uvicorn src.api.main:app --reload        # API on http://127.0.0.1:8000

# frontend (second terminal)
npm --prefix frontend install
npm --prefix frontend run dev                      # http://localhost:5173 (proxies /api/* to :8000)
```

Note: the Vite dev server answers on `localhost` (IPv6). In a terminal
`curl http://127.0.0.1:5173/health` fails (connection refused) while
`curl http://localhost:5173/health` returns
`{"status":"ok","service":"wasterouting-api"}` [observed live run 2026-11-14].
Open **http://localhost:5173** in a browser.

Checks (same as `.github/workflows/ci.yml`; all green 2026-11-14 on the v4
tree):

```bash
.venv/bin/ruff check .        # lint (use the venv binary — plain `ruff` may not be on PATH)
.venv/bin/mypy src            # strict type check → 0 issues in 39 files
.venv/bin/pytest              # backend tests → 573 passed
npm --prefix frontend test    # Vitest → 97 passed (20 files)
npm --prefix frontend run build
```

Comparison CLI (regenerates the comparison part of `docs/demo_numbers.md`;
the scenario-engine section of that file is recorded from live
`POST /api/scenarios` / `POST /api/simulation` calls):

```bash
.venv/bin/python -m src.api.compare_demo
```

## 3. Demo walkthrough (screens)

Start both servers, open http://localhost:5173. On the **Overview** page,
press **Load demo data** (loads the server-side demo CSV; the response labels
the source `demo:`) or upload `data/raw/glass_fill_levels_anonymized_f.csv`
via the upload panel. Both produce identical results.

### Overview
Three plain-language key numbers from the live API [observed live run
2026-11-14]: 34.5 % of emptying records are at/above the 80 % threshold,
10.2 % are the literal `overfull` token (never coerced to 100), 0.0 % are
numeric 0. Shares are of **emptying records** — every row in the data is one
emptying event [representative-stated; written confirmation pending; JSON
field names keep the historical `readings` tokens]. Below: "Today's
recommendation" (how many series are expected to need emptying vs wait, with
example reasons and the as-of date), a how-it-works strip, and the
**before/after comparison card** (four-step story, §3.1).

### Four-step comparison story
Rendered from `GET /api/comparison` with the v4 defaults (container 3,000 L
and 5 min emptying [representative], 10 min per leg [representative +
interpretation], density 0.40 kg/L [literature — German AVV table AVV
20 01 02, entsorgen-versorgen.de, retrieved 2026-11-14], 500 EUR/truck-day
[representative]); numbers are the generated run in `docs/demo_numbers.md`.
All distances are haversine-straight-line-derived, **never road distance**.
Every step shows cost **with its service level** — the observed anchor
[observed] is 26.9 % of emptying records full/overfull:

| step | scenario | distance | served | m per kg | cost/day | cost/year |
|---|---|---|---|---|---|---|
| 1. Status quo (28-d fixed cycle [demo assumption, Q10]) | `naive_fixed_frequency` (637 series due) | 355,474 m | 60 / 637 | 10.5 | 1,500 EUR | 300,000 EUR |
| 2. Sweep-all upper bound | `naive_sweep_all` (all 1,338 series, fixed area sweep) | 454,623 m | 50 / 1,338 | 12.6 | 1,500 EUR | 300,000 EUR |
| 3. Selection effect | `naive_sweep_selected` (policy-selected 458 only) | 527,021 m | 38 / 458 | 13.2 | 1,500 EUR | 300,000 EUR |
| 4. Optimised routing | `ortools` | 70,175 m | 34 / 458 | 3.9 | 1,500 EUR | 300,000 EUR |

Gains: selection **−72,398 m** (visiting fewer stops with the same sweep
order did not pay off per metre — the UI words negative gains honestly),
routing **+456,846 m**, total **+384,448 m**. Served counts differ between
scenarios by design, so the like-for-like comparison is the **m per
collected kg** column (10.5 → 12.6 → 13.2 → 3.9); never read raw distances
as equivalent. Under the flat 10-min travel mode, visiting **order cannot
change duration** (§4.4) — time/cost differences come from stop *selection*,
not routing order; distance differences are distance only. Cost columns are
[predicted] derivations — 3 trucks × 500 EUR/truck-day [representative] ×
200 operating days/year [representative] — never invoiced amounts, always
shown beside the 26.9 % service anchor. The card also shows the **fleet
budget** implied by the optimised run: 99 × `demo_truck` = 49,500 EUR/day /
9,900,000 EUR/year [predicted, covers full demand incl. unserved stops].

### Containers (list + interval view)
Two views over the same 1,338 series:

- **Series list**: last emptying-record date, last fill (numeric or
  `overfull`, never coerced), and record count.
- **Per-container interval view** (§5.2.3 v2): rate in %/day, median
  emptying interval, days-to-full (target 90 % [demo assumption — slide
  mockup]), and the predicted-full date (may be overdue — never clamped).
  Rows whose contributors include a numeric 100 or an `overfull` record are
  **censored lower bounds** and carry an explicit "at least" marker (real
  demand ≥ estimate; 66.5 % of estimates are flagged [predicted]); rows
  without an estimate show the API reason (`not_enough_records`,
  `zero_interval_only`, `no_numeric_fill`, `zero_rate`) instead of a
  fabricated number. Filters: material, only lower bounds, only missing
  estimates, text search. The mandatory caveat — *"fill at emptying shows
  how full the container was when the schedule reached it — not how fast it
  would have filled"* — is rendered beside the rates [representative-stated;
  rates additionally assume no unobserved emptyings between records].

### Forecast & candidates
Pick an as-of date (defaults: as_of 2026-09-30, horizon 28 days
[demo assumption — the observed median emptying interval]) and method:
**`rate` is now the stronger baseline** under the v4 emptying-record
semantics — test MAE 20.15 pp vs persistence 22.76 pp [predicted,
chronological split, `docs/model_card.md`]; persistence remains available.
The candidates panel shows selected vs skipped series with reason badges
(`at_or_above_threshold`, `overfull_state`, `below_threshold`,
`no_forecast`) and the deciding numbers in each detail string. Demo run:
458 selected / 880 skipped [observed live run 2026-11-14].

### Route map
`POST /api/route` runs forecast → policy → geography → OR-Tools. The map
draws routes with numbered stops plus depot/disposal icons; the route panel
shows totals, load progression, the fleet recommendation, cost, and **every
unserved stop with its reason** (never silently dropped). Demo run (ortools
scenario, `docs/demo_numbers.md`): status `feasible`, 3 routes, 34 of 458
candidates served / 424 unserved with reasons, 70,175 m / 580 min,
45,000 L / 18,000 kg (density 0.40 kg/L [literature]), fleet
recommendation 99 × `demo_truck` (basis: ceil_by_volume 99, ceil_by_weight
48), scenario cost 1,500 EUR/day [predicted]. An interactive `POST
/api/route` under the same defaults returns the same status and invariants;
served counts may differ within the solver protocol (contracts §4.4). A
banner marks the synthetic demo geography; coordinates are synthetic until
the host supplies real ones [demo assumption].

### Days to full
`GET /api/days-to-full` answers the representative's reporting wish
("average days-to-full per container") [predicted], method
`fill_at_emptying_rate` (§5.2.3 v2). Per series: the rate is the median over
emptying records of `fill at that emptying / interval days` (positive
intervals, numeric fills only — never Δfill/Δdays, §1.5);
`days_to_full = target_pct / rate` with target 90 % [demo assumption — slide
mockup]; `predicted_full_date = last emptying date + round(days_to_full)`,
never clamped (it may lie in the past — "overdue"). Records at numeric 100
or `overfull` are censored lower bounds: they never enter the numeric median
but flag `is_lower_bound` (real demand ≥ estimate). Series without an
estimate get a reason (`not_enough_records`, `zero_interval_only`,
`no_numeric_fill`, `zero_rate`) — never a fabricated number. Demo run on
the real CSV (target 90): 1,303 / 1,338 series with an estimate, median
59.3 d, mean 101.7 d, min 6.6, max 2,313.0 d, 66.5 % flagged lower bounds
[predicted; per-material medians: brown 121.95 / green 52.0 / white 38.05
days]. Caveats echoed in `assumptions`: the container is assumed to refill
from 0 after each emptying [model assumption], the median emptying interval
is 28 d [observed], and rates assume no unobserved emptyings between
records — indicative, not a schedule.

### Scenarios (planning levers; cost AND service level together)
`POST /api/scenarios` + `POST /api/simulation` power the Scenarios tab
(§5.2.4/§5.2.5). Sliders (initialised from `GET /api/config` defaults — the
panel hardcodes no thresholds, costs, capacities or frequencies; bounds are
UI ergonomics only): collection cycle `frequency_days` (default 28
[demo assumption — real schedule unknown, Q10]), `containers_per_series`
(Q11), cost per truck-day, shift length, vehicle volume. Two strategies are
replayed over the observed window on per-series fill-at-emptying rates
[predicted]:

| strategy | emptyings | truck-days | cost total | cost/year | overflow share | simulated emptyings full/overfull | max fill |
|---|---|---|---|---|---|---|---|
| `fixed_frequency` (every 28 d) | 15,636 | 852 | 426,000 EUR | 244,126.07 EUR | 2.4 % | 14.4 % | 366.4 % |
| `demand_driven` (≥ 80 % predicted) | 9,993 | 1,040 | 520,000 EUR | 297,994.27 EUR | 0.0 % | 0.0 % | 80.0 % |

Observed anchor [observed]: 26.9 % of emptying records full/overfull —
rendered as the reference beside every simulated cost. The honest §6 result
[live run 2026-11-14]: `fixed_frequency` is cheaper but overflows;
`demand_driven` eliminates overflow (max fill exactly the 80 % trigger) yet
**costs more** — its emptyings cluster onto shared peak days (rate-
synchronised series come due together), so peak days need more trucks
despite fewer total emptyings. The UI always shows both numbers; a strategy
that lowers cost while worsening service is visibly flagged, and cost is
never shown alone. The timeline chart carries the **mega-day note**: series
without pre-window history start at fill 0 on the same day, so the replay
synchronises onto ~12 mega-days of ~1,303 emptyings — a replay artefact of
the §5.2.5 initialisation rule (clock starts at each series' latest record ≤
`start_date`; leakage-safe), not observed behaviour. TechDetails show the
calibration echo: simulated fill-at-emptying median 42.5 % vs observed
60.0 %.

### Presentation mode
A 6-slide, big-type walkthrough (←/→ navigation, Esc closes, native
fullscreen) built from the same live responses — comparison, scenarios,
days-to-full, candidates. Every slide keeps the honesty labels ([observed] /
[predicted] / simulation basis, straight-line distance, [representative] /
[demo assumption] tags); a slide whose data is missing renders an explicit
"data not available" note instead of a fabricated number. Use it as the
demo opener and closer (`docs/demo_script.md`).

### Config editor
Edits 3 policy fields and the routing config (container volume, densities,
vehicle capacities/count/compartments, service times, shift, travel-time
mode + fixed minutes, cost parameters, geography knobs, solver budget, plus
the v4 knobs `containers_per_series` [Q11] and `frequency_days` [Q10]);
empty = inherit the default. Every default is tagged via the
`assumption_fields` list and carries its per-field source in the `sources`
map from `GET /api/config` (`representative`, `literature` or
`demo assumption`) — the UI keeps the distinction visible, and overrides
never re-label a value as a fact.

### Technical details & determinism
The collapsible technical-details block shows the solver status and the
distance provenance (`haversine_straight_line_derived`). The optimised
scenario is solved 5 times [demo assumption]; the UI shows the determinism
mode: `identical` (all runs equal — the demo case, 70,175 m × 5) or
`median_of_runs` with min/median/max. A fired wall-clock safety cap produces
status `timeout`, which is explicitly non-reproducible and never shown as
deterministic.

## 4. Technical architecture

```text
challenge CSV ──► src/data (loader/validation) ──► src/analytics (EDA)
                         │
                         ▼
              src/forecasting (persistence/rate baselines, days-to-full)
                         ▼
              src/collection (threshold policy → candidates)
                         ▼
    src/routing (demo geography/fleet + OR-Tools solver) ──► src/api (FastAPI)
                                                              ▼
                                                     frontend (React dashboard/map)
```

Module responsibilities follow `PLAN.md`; cross-module shapes are pinned in
`docs/contracts.md`. API endpoints (contracts §5, all JSON snake_case,
routers under `/api`): `GET /health` (root + `/api/health`), `POST
/api/datasets` (CSV upload), `POST /api/datasets/demo`, `GET /api/summary`,
`GET /api/containers`, `GET /api/config`, `POST /api/forecasts`, `POST
/api/candidates`, `POST /api/route`, `GET /api/comparison`, `GET
/api/days-to-full`, `POST /api/scenarios` (§5.2.4 cost + service level),
`POST /api/simulation` (§5.2.5 daily replay). Handlers are thin;
orchestration lives in `src/api/services.py`. Forecast approach:
deterministic persistence/rate baselines with leakage-safe features and a
chronological split (train < 2026-05-01, test ≥ 2026-08-01) — see
`docs/model_card.md`; under v4 semantics the **rate** baseline leads (test
MAE 20.15 pp vs persistence 22.76 pp [predicted]) and ML (M6) stays
deferred until a model beats 20.15 pp. Routing approach: OR-Tools CVRP with
per-material compartment dimensions plus a weight dimension, disposal
unload-reset, droppable stops, solution-limit stopping, `fixed_per_leg`
travel times (10 min on every leg incl. depot/disposal [representative +
interpretation]) — full method in `docs/routing_methodology.md`. Comparison
design (four scenarios incl. the fixed-frequency status quo, gains, cost/
fleet-budget derivations, repetition protocol): contracts §4.7 and §5.2.2;
scenario engine and replay: §5.2.4/§5.2.5.

## 5. Limitations (all labelled, not hidden)

- **One dataset in memory.** Uploads replace the active dataset; no
  persistence beyond the process.
- **Private raw CSV.** The challenge CSV is private and git-ignored: the
  **Load demo data** button, `POST /api/datasets/demo` and the real-data
  tests (real-CSV pins + demo-endpoint tests) require it at
  `data/raw/glass_fill_levels_anonymized_f.csv` (path is the server-side
  constant in `src/api/services.py`). On a clean checkout without the file,
  those tests skip with an explicit reason (`tests/helpers.py`) and the
  demo endpoint responds 404 by design — place the CSV at that exact path
  to enable both.
- **Representative / literature inputs, not confirmed specs.** Container
  3 m³, 5 min emptying, 10 min driving per leg, 8 h shift and 500
  EUR/truck-day (5 days/week, 200 days/year) came verbally from the
  challenge representative [representative]; the flat 10 min on **every**
  leg incl. depot→first/last→depot/disposal is our interpretation of
  "10 min between containers" (open question Q4). Density 0.40 kg/L is
  [literature] (German AVV table AVV 20 01 02, entsorgen-versorgen.de,
  retrieved 2026-11-14; Q2). Fleet specs, compartment layout, disposal
  unload time and all coordinates remain [demo assumption]
  (`docs/open_questions.md` Q1, Q3, Q6, Q8; road network Q7; schedule Q10;
  containers per site Q11). All are defaults in
  `src/routing/demo_config.py`, overridable per request.
- **Straight-line-derived distances.** Distances are haversine × 1.4
  detour factor [demo assumption]; there is no road-network data [observed].
  Never called road distance anywhere in the product.
- **Emptying-record semantics pending written confirmation.** One row =
  one emptying event; fill = level at that emptying
  [representative-stated, 14 Nov 2026; written confirmation pending].
  Consequence for every rate/days-to-full number: fill at emptying shows
  how full the container was when the schedule reached it — not how fast it
  would have filled; rates assume no unobserved emptyings between records
  (§1.5 caveat, rendered in the UI). JSON field names keep the historical
  `readings` tokens.
- **Simulation is a model, not a prediction.** Scenario/simulation numbers
  are [predicted] replays of historical rates — no seasonality, holiday or
  weather effects; series without pre-window history start at fill 0 on
  the same day and synchronise onto "mega-days" (replay artefact, §5.2.5,
  labelled in the timeline); calibration gap echoed (simulated fill-at-
  emptying median 42.5 % vs observed 60.0 % [predicted/observed]).
- **Cost figures are derivations, never invoices.** All EUR amounts are
  [predicted] products of `vehicles_used` / fleet size × the [representative]
  cost parameters — no invoiced or tendered amounts exist.
- **Days-to-full is indicative.** [predicted] from emptying records only;
  assumes the container refills from 0 after each emptying [model
  assumption] and rates assume no unobserved emptyings between records;
  the median emptying interval is 28 d [observed]; 66.5 % of estimates are
  censored lower bounds (real demand ≥ estimate).
- **Persistence baseline only.** M6 (ML) is deferred; persistence test MAE
  22.76 pp [predicted] is the current bar.
- **Solver determinism protocol.** Repeated solves that reach the fixed
  solution budget are identical; only a fired safety-cap timeout
  reintroduces wall-clock variance.
- **Small served share.** With the demo fleet ×3 [demo assumption] and the
  8 h shift [representative], most candidates remain unserved with reasons —
  honest feasibility surfacing, not a bug.
- **Python floor ≥3.12.** `requires-python = ">=3.12,<3.15"` because numpy
  2.5.4 requires ≥3.12 (earlier conflict with the 3.11 floor fixed in commit
  e6db442, 2026-11-14; `uv.lock` is committed so resolutions reproduce).
